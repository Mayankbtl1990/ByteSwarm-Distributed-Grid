## 1. Week 3 Objective

The main objective of Week 3 was to make the distributed compute grid more reliable.

During Week 2, ByteSwarm was able to:

* Split jobs into chunks.
* Dispatch chunks to workers.
* Execute computation inside browser Web Workers.
* Track worker load.
* Collect computation results.
* Display basic swarm metrics.

The main weakness was that the system depended on workers remaining connected and responding correctly.

Week 3 therefore focused on:

1. Detecting failed or stale workers.
2. Detecting chunks that become stuck.
3. Reassigning work from failed workers.
4. Recovering WebSocket connections.
5. Monitoring worker and job health.
6. Displaying recovery information on the dashboard.
7. Improving topology visualization.
8. Improving backend recovery metrics.

The GitHub history confirms these changes through commits such as `add hearbeatmanager to detect dropped workers`, `feat(chunking): detect stuck chunks with ChunkTimeoutDetector`, and `implement dropped worker chunk reassignment`.

# 3. Day 1 — Worker Health & Chunk Timeout Detection

## 3.1 Heartbeat Manager

A `HeartbeatManager` was introduced to monitor worker health.

The purpose is to periodically determine whether workers are still alive.

The GitHub history contains the commit:

```text
add hearbeatmanager to detect dropped workers
```

and later:

```text
add stale worker monitor and backend health scan startup
```

These changes were committed by Bhanu and integrated into the project.

### Responsibilities

The heartbeat system:

* Monitors connected workers.
* Tracks worker activity.
* Detects stale workers.
* Identifies workers that stop responding.
* Triggers recovery processing when a worker disappears.

### Result

The backend can now distinguish between:

```text
ACTIVE WORKER
      |
      v
HEALTHY
```

and:

```text
STALE / DROPPED WORKER
      |
      v
RECOVERY PROCESS
```

# 4. Chunk Timeout Detection

Week 3 also introduced chunk timeout detection.

The relevant commit was:

```text
feat(chunking): detect stuck chunks with ChunkTimeoutDetector
```

with commit:

```text
b4687f0
```

A missing `ChunkingEngineTest` was subsequently added to support the functionality.

## Purpose

A chunk may become stuck when:

* A worker crashes.
* A WebSocket connection disappears.
* A browser tab is closed.
* A worker stops processing.
* A result is never returned.

Instead of waiting indefinitely, the backend can detect that the chunk has exceeded its expected execution period.

### Conceptual Flow

```text
Chunk Assigned
     |
     v
Start Timer
     |
     +------ Result received ------> SUCCESS
     |
     |
     +------ Timeout -------------> STUCK
                                      |
                                      v
                               Recovery Process
```

# 5. Day 2 — Dropped Worker Chunk Reassignment

One of the most important Week 3 features was worker failure recovery.

The repository contains the commit:

```text
implement dropped worker chunk reassignment
```

with commit:

```text
803a51b
```

and related backend commits:

```text
reclaim and requeue chunks on worker drop
```

```text
8a81367
```

These changes were merged into `main`.

## Problem

Suppose a job contains:

```text
Chunk 1 -> Worker A
Chunk 2 -> Worker B
Chunk 3 -> Worker C
Chunk 4 -> Worker D
```

If Worker B crashes:

```text
Chunk 2 -> Worker B
             X
          Worker dead
```

Previously, the chunk could remain associated with the failed worker.

## New Behaviour

```text
Worker B fails
      |
      v
Heartbeat detects failure
      |
      v
Find chunks assigned to Worker B
      |
      v
Remove stale assignment
      |
      v
Requeue chunks
      |
      v
Chunk Dispatcher
      |
      v
Select healthy worker
      |
      v
Execute chunk again
```

This provides automatic recovery without requiring the user to restart the job.

```text

```

The backend was also refined through PR #59:

```text
refine backend startup and websocket recovery stability
```

## Exponential Backoff

Instead of reconnecting continuously:

```text
Reconnect
Reconnect
Reconnect
Reconnect
...
```

the client progressively waits:

```text
Attempt 1 -> short delay
Attempt 2 -> longer delay
Attempt 3 -> longer delay
Attempt 4 -> longer delay
```

This reduces unnecessary connection pressure on the server.
